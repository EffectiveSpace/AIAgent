## 1. Введение: Проблема цифровой амнезии

Представьте, что вы наняли гениального, но невероятно забывчивого ассистента. Вы даете ему задачу: «Найди мне лучшие рестораны итальянской кухни в центре Москвы». Он мгновенно выдает вам список. Вы уточняете: «Отлично! А теперь отфильтруй те, что открыты после 23:00». И в ответ получаете: «Отфильтровать что? О каких ресторанах идет речь? Мы с вами раньше общались?». 

**Абсурд? Да. Но именно так по умолчанию ведет себя любой ИИ-агент, построенный на вызовах к API больших языковых моделей (LLM)**.

Каждый ваш запрос для него — это новая, чистая вселенная, не связанная с предыдущей. Он не помнит ни ваших инструкций, ни своих ответов. Это фундаментальная проблема, которая превращает потенциально мощного партнера в бесполезный "одноразовый" калькулятор.

### Почему это критично?

В реальной жизни мы постоянно опираемся на контекст — на все, что уже произошло в диалоге. Без памяти невозможно поддерживать связный разговор, вести долгосрочный проект или учиться на ошибках. ИИ-агент без памяти — это как машина без тормозов: может быть мощной, но небезопасной и непредсказуемой.

## 2. Что такое контекстное окно? Фундамент краткосрочной памяти

Если LLM — это мозг нашего агента, то **контекстное окно (context window)** — это его **оперативная память (RAM)**. Это не какая-то мистическая область внутри серверов OpenAI, а простая концепция: максимальное количество информации (измеряемое в токенах), которое можно одновременно передать в LLM в рамках одного API-запроса.

**Важно понимать**: *LLM сама по себе ничего не помнит.* Память — это иллюзия, которую мы, разработчики, создаем для пользователя. Механизм этой иллюзии основан на структуре запросов к современным чат-ориентированным моделям.

### Структура запроса к LLM

Вместо старого подхода с текстовыми промптами, современные модели (вроде GPT-4, Claude 3) принимают **структурированный массив сообщений**. Каждое сообщение имеет:

1. **role (роль)**: Кто отправитель
   - `system`: Инструкции, личность, правила поведения
   - `user`: Сообщение от пользователя
   - `assistant`: Ответ, сгенерированный моделью

2. **content (содержимое)**: Текст сообщения

Пример структуры:
```json
{
  "model": "gpt-4-turbo",
  "messages": [
    {
      "role": "system",
      "content": "Ты — полезный ассистент, говорящий кратко и по делу."
    },
    {
      "role": "user", 
      "content": "Привет! По каким дням недели работает ваш магазин?"
    },
    {
      "role": "assistant",
      "content": "Привет! Наш магазин работает с понедельника по пятницу, с 9:00 до 18:00."
    },
    {
      "role": "user",
      "content": "А в субботу?"
    }
  ]
}
```

Вот он, ключ к "памяти": модель "видит" и обрабатывает **все** сообщения в этом массиве. Она читает всю предыдущую переписку и "помнит", что вы уже спрашивали про будни. Мы не просим её "вспомнить" — мы просто **всегда отправляем полный контекст**.

## 3. Токены: Валюта контекста

Ключевая единица измерения здесь — **токен**. Это не слово и не символ, а **элементарная семантическая единица**, на которые модель разбивает текст.

- Короткие и частые английские слова часто равны одному токену: `the`, `a`, `is`
- Более длинные слова разбиваются на части: `tokenization` -> `token`, `ization`
- В русском языке из-за сложной морфологии на одно слово обычно приходится больше токенов: `автоматизация` -> `автомат`, `изац`, `ия`

### Почему это критически важно?

1. **Лимит**: Размер контекстного окна измеряется именно в токенах. 
   - GPT-4 Turbo: 128,000 токенов
   - Claude 3 Opus: 200,000 токенов
   - Llama 3 (локально): 8,192 токенов
   Эти объемы огромны (до 2500 страниц текста!), но **не бесконечны**.

2. **Стоимость**: Вы платите за каждый токен, который отправляете в модель (входные токены) и за каждый токен, который она генерирует в ответ (выходные токены). Длинная история диалога, отправляемая снова и снова, **прямо влияет на стоимость** работы вашего агента.

3. **Производительность**: Большие контексты требуют больше времени на обработку, что влияет на скорость отклика.

## 4. Механика памяти: Как на самом деле LLM "вспоминает"

Представьте контекстное окно как доску для записей. 
1. Перед тем как задать новый вопрос, вы стираете с доски все, что было
2. Пишете на ней всю предыдущую переписку
3. Добавляете новый вопрос
4. Показываете доску модели
5. Модель читает все, что на доске, пишет свой ответ и отдает доску вам
6. Для следующего вопроса вы повторяете процесс

**Вся "память" — это то, что вы сами неустанно пишете на этой доске перед каждым обращением.**

### Пример работы

Пользователь: «Привет! Посоветуй книгу по научной фантастике».

```json
  "messages": [
    {
      "role": "system",

    },
    {
      "role": "user",
      "content": "Привет! Посоветуй книгу по научной фантастике."
    }
  ]

```

Модель отвечает: «Конечно! Рекомендую "Дюну" Фрэнка Герберта. Это вечная классика».

## 5. Практика: Создаем агента с базовой краткосрочной памятью на Python

### Шаг 1: Наивный подход и его проблемы

```python
import os
from openai import OpenAI
from dotenv import load_dotenv

# Загружаем переменные окружения
load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

# Просто список для хранения истории
chat_history = [
    {"role": "system", "content": "Ты — полезный AI-ассистент. Твоя задача — поддерживать диалог."}
]

print("Агент готов к диалогу. Введите 'выход', чтобы закончить.")

while True:
    user_input = input("Вы: ")
    if user_input.lower() == 'выход':
        print("Агент: До свидания!")
        break
        
    # Добавляем сообщение пользователя в историю
    chat_history.append({"role": "user", "content": user_input})
    
    try:
        response = client.chat.completions.create(
            model="gpt-3.5-turbo",  # Используем быструю и дешевую модель для теста
            messages=chat_history
        )
        assistant_message = response.choices[0].message.content
        print(f"Агент: {assistant_message}")
        
        # Добавляем ответ ассистента в историю
        chat_history.append({"role": "assistant", "content": assistant_message})
        
    except Exception as e:
        print(f"Произошла ошибка: {e}")
        # В случае ошибки удаляем последний вопрос пользователя, чтобы не засорять историю
        chat_history.pop()
```

**Проблемы этого подхода**:
1. **Бесконечный рост**: Список `chat_history` растет с каждым обменом репликами. После длинного диалога он станет огромным.
2. **Превышение лимита**: Рано или поздно суммарное количество токенов в `chat_history` превысит лимит контекстного окна модели (например, 128,000 для gpt-4-turbo), и вы получите ошибку от API.
3. **Высокая стоимость**: Каждый раз мы отправляем всю, даже самую старую и, возможно, уже нерелевантную историю, оплачивая её токенами снова и снова.

### Шаг 2: Создание класса ConversationMemory

Чтобы решить эти проблемы, нужно инкапсулировать логику управления памятью в отдельный класс.

```python
# memory_manager.py
class ConversationMemory:
    """
    Простой класс для управления краткосрочной памятью агента (историей диалога).
    Использует базовую стратегию обрезки "sliding window" (скользящее окно).
    """
    
    def __init__(self, system_prompt: str, max_messages: int = 10):
        """
        Инициализация памяти.
        
        :param system_prompt: Системный промпт, который всегда будет в начале истории.
        :param max_messages: Максимальное количество сообщений (user + assistant) для хранения.
                             Системный промпт не считается в этом лимите.
        """
        self.system_prompt = {"role": "system", "content": system_prompt}
        # Умножаем на 2, т.к. храним пары "вопрос-ответ"
        self.max_messages = max_messages * 2  
        self.buffer = []
    
    def add_message(self, role: str, content: str):
        """Добавляет сообщение в буфер памяти."""
        self.buffer.append({"role": role, "content": content})
        self._prune()
    
    def _prune(self):
        """
        Обрезает буфер, если он превышает max_messages.
        Удаляет самые старые сообщения, сохраняя недавние.
        """
        if len(self.buffer) > self.max_messages:
            # Удаляем N самых старых сообщений, где N - превышение лимита
            num_to_prune = len(self.buffer) - self.max_messages
            self.buffer = self.buffer[num_to_prune:]
    
    def get_history(self) -> list:
        """
        Возвращает историю в формате, готовом для передачи в API.
        Системный промпт всегда добавляется в начало.
        """
        return [self.system_prompt] + self.buffer
    
    def clear(self):
        """Полностью очищает историю диалога."""
        self.buffer = []
```

**Что делает этот класс**:
1. **В `__init__`** принимает системный промпт и максимальное количество сообщений. Системный промпт всегда сохраняется отдельно.
2. **`add_message`** просто добавляет новое сообщение в список `buffer`.
3. **`_prune`** — это наша стратегия управления памятью. После каждого добавления она проверяет лимит и при необходимости "срезает" самые старые сообщения. Это простейшая реализация **"скользящего окна"**.
4. **`get_history`** формирует финальный список, который мы передадим в API, всегда ставя системный промпт на первое место.

### Шаг 3: Интеграция ConversationMemory в основной цикл

```python
# main_agent.py
import os
from openai import OpenAI
from dotenv import load_dotenv
from memory_manager import ConversationMemory  # Импортируем наш класс

# Загружаем переменные окружения
load_dotenv()

# Инициализируем клиент OpenAI
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

# Создаем экземпляр нашей памяти
# Будем хранить последние 5 пар "вопрос-ответ"
agent_memory = ConversationMemory(
    system_prompt="Ты — полезный AI-ассистент по имени 'Агент-006'. Твоя задача — поддерживать осмысленный диалог. Отвечай кратко, но информативно.",
    max_messages=5
)

print("Агент-006 готов к диалогу. Введите 'выход', чтобы закончить.")

while True:
    user_input = input("Вы: ")
    if user_input.lower() == 'выход':
        print("Агент-006: Миссия выполнена. До связи!")
        break
    
    # 1. Добавляем сообщение пользователя в память
    agent_memory.add_message(role="user", content=user_input)
    
    try:
        # 2. Получаем полную историю для API из нашего менеджера памяти
        messages_to_send = agent_memory.get_history()
        
        response = client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=messages_to_send
        )
        
        assistant_message = response.choices[0].message.content
        print(f"Агент-006: {assistant_message}")
        
        # 3. Добавляем ответ ассистента в память
        agent_memory.add_message(role="assistant", content=assistant_message)
        
    except Exception as e:
        print(f"Произошла ошибка: {e}")
        # Если что-то пошло не так, можно реализовать логику отката,
        # но наш класс памяти уже достаточно устойчив.

print("Диалог завершен.")
```

Теперь наш агент не только помнит диалог, но и **автоматически "забывает" слишком старые сообщения**, предотвращая переполнение контекстного окна и контролируя расходы.

## 6. Стратегии управления контекстом: Когда память не резиновая

Простое обрезание старых сообщений (Sliding Window) — это хорошо, но не всегда оптимально. Иногда в самом начале диалога содержится ключевая информация (например, «Моя цель — написать бизнес-план для кофейни»). Если мы её обрежем, агент потеряет главную цель.

Существуют более продвинутые стратегии управления краткосрочной памятью:

### 1. Окно с закреплением (Pinned Window / "Keep First")
- **Как работает**: Мы всегда сохраняем самое первое сообщение (обычно системный промпт) и, возможно, первый запрос пользователя. Обрезаются только сообщения между ними и самыми последними.
- **Преимущества**: Гарантирует, что агент никогда не забудет свою основную роль и первоначальную задачу.
- **Недостатки**: Чуть сложнее в реализации, чем простое скользящее окно.

### 2. Суммирование (Summarization)
- **Как работает**: Вместо того чтобы просто удалять старые сообщения, дополнительный вызов к LLM с просьбой: «Суммируй этот диалог в одном абзаце». Затем мы заменяем старые 10 сообщений этой сжатой сводкой.
- **Пример**: Вместо 10 сообщений о выборе ресторана у нас останется одно: `summary: "Пользователь искал итальянский ресторан в центре Москвы, открытый после 23:00. Мы обсудили варианты X и Y, пользователь склоняется к Y, но хочет проверить наличие вегетарианских блюд."`
- **Преимущества**: Позволяет сохранить суть очень длинных диалогов в компактной форме. Идеально для агентов-исследователей или аналитиков.
- **Недостатки**: 
  - Дополнительные затраты: Требует периодальных вызовов LLM для суммирования.
  - Потеря деталей: Суммирование по своей природе опускает нюансы, которые могут оказаться важными позже.

### 3. Память на основе токенов (Token-based Memory)
- **Как работает**: Вместо того чтобы считать сообщения, мы считаем токены. Перед отправкой запроса мы подсчитываем общее количество токенов в истории. Если оно превышает наш внутренний лимит (например, 3000 токенов, чтобы оставить запас для ответа), мы начинаем удалять старые сообщения, пока не впишемся в лимит.
- **Преимущества**: Самый точный и надежный способ избежать ошибки переполнения контекста.
- **Недостатки**: Требует наличия локального токенизатора (например, библиотека `tiktoken` для моделей OpenAI), чтобы точно считать токены без обращения к API.

## 7. Проблемы и ограничения краткосрочной памяти

### 1. Она недолговечна
Как только ваше приложение закрывается или сессия пользователя заканчивается, вся история в `ConversationMemory` исчезает. Агент не сможет вспомнить ваш вчерашний диалог. Для него каждый запуск — это новая жизнь.

### 2. Она конечна
Даже с окном в 200,000 токенов у Claude 3 Opus, вы не сможете «скормить» ему всю Википедию или всю вашу корпоративную базу знаний. Всегда есть предел.

### 3. Она дорогостоящая
Постоянно пересылать десятки тысяч токенов туда и обратно — это прямой путь к огромным счетам за API.

### 4. Проблема "Потери в середине" (Lost in the Middle)
Исследования показали, что LLM лучше всего обращают внимание на информацию в **начале** (системный промпт) и в **самом конце** (последний запрос) контекстного окна. Информация, "затерянная" где-то в середине длинной истории, имеет повышенный шанс быть проигнорированной моделью. Ваш агент может просто «не заметить» важную деталь из середины диалога.

Эти проблемы подводят нас к неумолимому выводу: **контекстное окно — это оперативная память, но не жесткий диск.** Оно идеально для поддержания текущего разговора, но **абсолютно не подходит для накопления знаний, опыта или воспоминаний о прошлых взаимодействиях**.

**Но амнезия после перезапуска — это серьезный барьер.** Наш агент все еще не способен учиться на своем опыте. Он не может запомнить ваши предпочтения, факты о вашем проекте или успешные решения, которые он находил в прошлом. Он обречен вечно наступать на одни и те же грабли.

Как дать ему доступ к «жесткому диску»? Как научить его извлекать релевантные знания из огромного массива информации, а не только из последних десяти сообщений? Как заставить его "помнить" не только текущий разговор, но и прошлые сессии?

Для этого нам понадобится совершенно другой, куда более элегантный и мощный механизм — **долгосрочная память на основе векторных баз данных и магии эмбеддингов**, которую мы изучим в следующей главе.

В следующей главе мы решим проблему цифровой амнезии по-настоящему: научим нашего агента **хранить знания**, **по-настоящему запоминать** информацию и **находить нужные сведения** среди огромных объемов данных. Мы разберем, что такое embeddings (встраивания) и как они превращают любой текст в математический "отпечаток смысла". Мы погрузимся в мир векторных баз данных (ChromaDB, FAISS) — специализированных хранилищ для этих "отпечатков". И, конечно же, мы построим нашего первого агента с **действительно умной, несмываемой памятью**.
